How the system really works

Only the core logic: what each part does, how the data moves, and exactly when files get combined. No Docker, no setup. Everything with a ▶ is animated.

1. Your question, answered first

Do we collect all the partial results and then combine them? Or do we combine whenever a worker is free?

The second one, with a small twist. We never wait for everything. Each job has a basket of finished pieces. Every time any worker finishes something, the scheduler looks in the basket and decides whether to start a new combine task right now. So combining starts while files are still being generated, and the last combine is the only one that divides.

What we do NOT do
  • Generate all F files first, then start combining (workers would sit idle, and the disk fills up first).
  • Build a fixed tree in advance ("pair file 1 with file 2…"). Workers have different speeds, so a fixed plan would stall on the slowest.
What we do
  • Keep a basket of ready pieces.
  • Whenever a result arrives, look at the basket and decide (4 simple rules, section 6).
  • A fast worker finishes sooner, so it comes back sooner and takes more work. Nothing is pre-assigned.

2. The one idea everything rests on: a piece is "sums + count"

A job has F files, each a list of C numbers. We want, for every position, the mean over all F files. One worker may only hold 5 files, so we need partial answers that can be merged later. The partial answer must never be an average, because averages of groups with different sizes can't be merged. Instead every piece carries:

  • sums: a list of C numbers (for each position, the total of the files it covers)
  • count: how many original files it covers

A freshly generated file is already a valid piece: its sums are the file itself and its count is 1. Merging any pieces = add position by position, add the counts. You divide once, at the very end.

example: C = 3 numbers per file, F = 2 files
position 0position 1position 2count
file A (piece)1231
file B (piece)4561
merge = add column by column5792
final = divide by count (once)2.53.54.5÷ 2
Why not just average the averages? Take one position with values 1, 1, 1, 1, 1, 7. True mean = 12 / 6 = 2. If a group of 5 gives average 1 and a group of 1 gives average 7, the average of those is 4. Wrong, because the single file got the same weight as five. With sums and counts: (5 + 7) / (5 + 1) = 2. Right, in any order and any grouping. That freedom is what lets workers combine whatever is ready.

3. Who does what

PartIts one jobDoes it touch the big numbers?
ClientSays "F files, C numbers each". Later checks progress and downloads the result.No
APIChecks the request, creates the job, and splits it into GENERATE tasks of up to 5 files each (F = 12 gives 3 tasks: files 0–4, 5–9, 10–11). Answers status questions.No
DatabaseThe notebook. Remembers every job, every task and its status, and every piece (its file path, its count, and whether it is READY in the basket or USED by a combine).No, only paths and counts
Task queueThe hand-out line. Tasks wait here. A worker takes one at a time, so whoever is free first gets the next one.No
WorkerDoes exactly one task, then asks for another. It does not know the big picture. GENERATE: make up to 5 random files and save them. COMBINE: read up to 5 pieces from disk (one at a time), add them, save the new piece.Yes
Results queueWorkers drop a tiny "I'm done, here are the new piece paths and counts" note here.No
Scheduler + plannerThe brain. Reads one result at a time, updates the notebook, then asks the planner: "given what's in the basket, should I create a combine task now?"No
Shared diskWhere all the big arrays live. Everyone else passes around paths.Yes (it is the data)
The key design choice: messages carry paths and counts, never the numbers. The numbers only travel between a worker and the disk.

      The four planner rules (the last one that fired is highlighted)

      #Condition (for one job)ActionWhy
      1Basket has 5 or more piecesTake 5 and create a COMBINE task now. Repeat while ≥ 5 remain.A full-size task is the most efficient use of a worker. No reason to wait.
      2Basket has 2 to 5 pieces, all files are generated, and no other task is queued or runningCreate the FINAL combine: add, then divide by the total count.Nothing else can ever arrive, so this is the last step.
      3Basket has 2 to 4 pieces, a worker is idle and nothing is waiting in the queueCombine what's there (not final).The worker would otherwise do nothing. Merging early keeps the basket small.
      4Exactly 1 piece, everything generated, nothing in flightFINAL task that only divides.Safety net so a job can never get stuck at the end.

      Otherwise: wait. If every worker is busy there's no point creating a tiny task that would just sit in line.

      6. Tracing F = 12 by hand (the default simulation, 3 equal workers)

      Untick "W3 is 3× slower" and press Reset to see exactly this. Times are simulated seconds.

      1. t = 0. 12 files become 3 GENERATE tasks: files 0–4, 5–9, 10–11. Each of the 3 workers takes one.
      2. t = 2. W3 had the short chunk (2 files), so it finishes first. Two pieces (f10, f11) land in the basket. A worker is idle and the queue is empty, so rule 3 merges them straight away. This happens while W1 and W2 are still generating.
      3. t = 3.6. W3 finishes: a partial P1 with count 2 goes into the basket.
      4. t = 5. W1 and W2 finish. The basket now holds 11 pieces (P1 and f0 … f9). Rule 1 fires twice: two COMBINE tasks of 5 pieces each. Groups can be any mix, because counts travel with the sums. W1 and W2 take them.
      5. t = 8.1. Both finish with partials of count 6 and 5. One loose piece (f9) is still in the basket. Everything is generated and nothing else is running, so rule 2 creates the FINAL task for those 3 pieces.
      6. t = 10.2. The final worker adds them (6 + 5 + 1 = 12 files), divides every position by 12 and writes result.csv. The scheduler checks count = 12 = F and marks the job COMPLETED. Any other count would mark the job FAILED instead of returning a wrong mean.

      With the slow W3 on, W3 just takes longer on its chunk. The others keep going and nobody waits for W3.

      8. The whole thing in ten lines

      1. Client asks for F files of C numbers.
      2. API cuts it into GENERATE tasks of ≤ 5 files and puts them in the queue.
      3. Each free worker takes one task, creates the files, writes them to disk, reports paths with count 1.
      4. The scheduler stores each new piece in the basket (database).
      5. After every result the planner looks at the basket and may create a COMBINE task (≤ 5 pieces).
      6. A worker takes that task, reads the pieces one at a time, adds position by position, writes a new piece with the summed count.
      7. The new piece goes back in the basket. Steps 5–7 repeat, overlapping with generation.
      8. When all files exist and nothing else runs, the planner creates the FINAL combine.
      9. The final combine divides by the total count and writes result.csv.
      10. The scheduler checks that the count equals F and marks the job COMPLETED.
