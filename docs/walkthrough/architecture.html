Distributed Mean: how it works

Note: file and function names here match the refactored code (see "Project structure" in the README). The code excerpts are shortened for reading; the real files carry more comments and typed names.

Start with the big picture, then Docker (what is actually running on your machine), then the code behind each box.

Part A: the high-level picture

1. What problem are we solving?

A user asks for a job: "take F files, each with C random numbers, and give me one file with the average of each position". Example: files [1,2,3] and [4,5,6] give [2.5, 3.5, 4.5].

F can be up to 99,999, so one machine can't do it quickly. Each worker can only hold 5 files at a time, and workers run at different speeds. So the system must split the job, hand pieces to many workers, and combine the pieces, all without anyone waiting for slow workers.

The kitchen analogy

In a restaurant kitchenIn our system
A big catering orderA job (F files of C numbers)
The waiter who takes the orderAPI (Express, TypeScript)
The order bookPostgreSQL: remembers every job, task and status
The ticket railRabbitMQ: queues of small tasks waiting for a cook
The cooks (some faster, some slower)Workers (Python): each takes one ticket at a time
The pantry everybody sharesShared folder /data: the actual number files
The head chef who watches finished dishes and decides what to cook nextScheduler: reads results, creates the next tasks
The one idea everything rests on. Every piece of work returns a list of per-position sums plus a count of how many files it covers, never an average. Adding sums and counts works in any order, so any worker can combine any pieces whenever they are ready. Divide once, at the very end. (This is the MapReduce pattern: generating files is the "map", combining is the "reduce".)

2. The architecture

Six parts. The numbers show the order things happen in for one task. Read the arrows as "sends something to".

  1. You create a job with POST /jobs {F, C} (from the dashboard or curl).
  2. The API saves the job and its first tasks in PostgreSQL (one "generate files" task per 5 files).
  3. The API puts the first few tasks on the tasks queue.
  4. A free worker takes one task from the queue. (Idle workers simply wait here.)
  5. The worker reads and writes files in the shared folder. Only file paths travel through the queue, never the numbers.
  6. When done, the worker puts a small "task X finished, output is at path Y, count Z" message on the results queue.
  7. The Scheduler reads that message.
  8. It updates PostgreSQL: task done, the new output goes into the job's "basket" of items waiting to be combined, and the planner decides whether to create a combine task.
  9. It publishes the next tasks onto the tasks queue (arrow 9), and the cycle repeats until the last combine task finishes. That one writes result.csv.

The API never talks to workers directly, and workers never talk to each other. Everything goes through the queues, the database and the shared folder. That is why workers can come and go freely.

3. The life of one job (step by step in time)

Same parts, now as a timeline. Each vertical line is one component; time flows downward.

Why a loop? A job with F=12 needs 3 generate tasks, then several combine tasks that only become possible after earlier results arrive. The scheduler creates each next task when its inputs exist, so the job unfolds as results come in.

4. How the pieces get combined (F = 12 example)

Each generate task makes up to 5 raw files. Each raw file is an item with count 1. The scheduler keeps a "basket" of items per job and combines up to 5 at a time as soon as they are ready.

  • Step 1: three generate tasks create the 12 raw files (5 + 5 + 2). Each file is an item with count 1.
  • Step 2: as soon as 5 items are ready, a combine task adds them index by index into a partial result (sums, count 5). This starts while other files are still being generated.
  • Step 3: when all 12 files exist, nothing else is running, and everything left fits in one task, the final task takes the rest (P1, P2, r10, r11), adds them (count 12) and divides once.

The exact grouping depends on timing (which result arrives first), but the answer is always identical, because adding sums and counts is order-independent. The scheduler checks that the final count equals F; if not, the job fails instead of returning a wrong answer.

Why not wait for all files, then combine?

Combining starts while other files are still being generated, so workers are rarely idle. A fast worker never waits for a slow one: it just takes the next ready task.

5. Docker: what is really running on your machine

You normally would have to install PostgreSQL, RabbitMQ, Node and Python with the right versions and wire them together. Docker packages each program with everything it needs, so one command starts the whole system the same way on any machine.

The four things Docker does for us

1. Builds our two images from a Dockerfile (a recipe):

# api/Dockerfile
FROM node:20-slim          # start from a ready-made Node image
WORKDIR /app               # work inside /app
COPY package.json package-lock.json ./
RUN npm ci                 # install dependencies
COPY tsconfig.json ./

RUN npm run build          # compile TypeScript to dist/
COPY public ./public       # the dashboard page

The scheduler reuses the same image as the API but runs a different command. Same code, two entry points.

2. Starts everything and wires it up (docker-compose.yml):

api:
  build: ./api
  command: node dist/server.js
  ports: ["3000:3000"]
  environment:
    DATABASE_URL: postgres://app:app@postgres:5432/jobs
    RABBITMQ_URL: amqp://guest:guest@rabbitmq:5672
    DATA_DIR: /data
  volumes: ["./data:/data"]
  depends_on:
    postgres: { condition: service_healthy }
    rabbitmq: { condition: service_healthy }
  • ports: "3000:3000" means your PC's port : container's port. This is why http://localhost:3000 reaches the API running inside its container.
  • The network: inside Docker, the API reaches the database at the hostname postgres and the queue at rabbitmq, using the service names from the compose file.
  • environment passes settings (URLs, passwords, limits) into containers, so the code has no hard-coded addresses.
  • volumes: "./data:/data" maps a folder on your disk into the container. Containers are throw-away, but files written to /data land in E:\Distributed Mean\data. All three code containers share it, which is how workers hand files to each other.
  • depends_on + healthcheck make Compose wait until Postgres and RabbitMQ are ready before starting the code that needs them. (RabbitMQ can report healthy slightly before it accepts connections, so our code also retries.)
  • Why one "workers" container but many workers? worker_manager.py starts W worker processes inside it and changes W when you call PUT /workers. That avoids giving the API control over Docker itself.

6. Statuses: what the database tracks

Everything the system "knows" is in a few PostgreSQL tables. The workers do not decide anything; they only run tasks. The scheduler moves things between statuses.

ThingStatuses and how they change
Job (jobs)
PENDING→ first result arrives →RUNNING→COMPLETED
or FAILED (a task failed 3 times, or final count ≠ F) · CANCELLED (user cancelled)
Task (tasks)
PENDING→ published to the queue →QUEUED→ result DONE →DONE
A failed result with attempts left sends it back to PENDING (retry). After 3 failures, or a cancel, it becomes FAILED.
Item (items, the "basket")
READY→ taken by a combine task →USED
Worker (workers)
IDLE ⇄ BUSY · DRAINING (finishing its task, then exiting) · DEAD (no heartbeat for 10 s)

Why PENDING and QUEUED are separate: a big job can have thousands of tasks. Only a small number are placed on the queue at a time (about 2 × W) so a huge job cannot block small jobs. The rest wait as PENDING in the database.

8. Creating a job: POST /jobs and publishPendingTasks()

Goal: validate, save the job and all its generate tasks in the database in one transaction, then put only the first few on the queue.

Step 1: validate and insert (one transaction)

// api/src/routes/jobs.ts
if (!isInt(F) || F <= 1 || F >= 100000) return res.status(400).json({ error: "F must be …" });
if (!isInt(C) || C <= 1 || C >= 1000000) return res.status(400).json({ error: "C must be …" });

const jobId = await withTransaction(async (client) => {
  const job = await client.query("INSERT INTO jobs (f, c) VALUES ($1, $2) RETURNING id", [F, C]);
  // ONE sql statement creates ceil(F/5) GENERATE tasks, each with up to 5 file indexes
  await client.query(
    `INSERT INTO tasks (job_id, type, payload)
     SELECT $1, 'GENERATE',
            jsonb_build_object('fileIndexes',
              (SELECT jsonb_agg(i) FROM generate_series(g * $3, LEAST(g * $3 + $3 - 1, $2 - 1)) AS i))
     FROM generate_series(0, ceil($2::numeric / $3)::int - 1) AS g`, [id, F, 5]);
  …
});
await publishPendingTasks();                      // publish the first batch
res.status(202).json({ jobId });

For F = 12 this makes three rows: files [0..4], [5..9], [10,11]. All start as PENDING. A transaction means either the job and all its tasks exist, or nothing does.

Step 2: publishPendingTasks() publishes a few tasks, fairly

// api/src/dispatch.ts
const target = Math.max(2, 2 * fleet.desired);        // keep the queue shallow: about 2 × W waiting
const slots  = target - fleet.waitingInQueue;         // how many more we may publish
if (slots <= 0) return 0;

// round-robin: 1st pending task of every job, then 2nd of every job, …
… ROW_NUMBER() OVER (PARTITION BY t.job_id ORDER BY t.created_at) AS rn …
   ORDER BY rn, job_created LIMIT $1
   FOR UPDATE OF t SKIP LOCKED

for (const t of rows) {
  await publish(TASKS_QUEUE, taskMessage(t, attempt));  // 1) publish and WAIT for the broker's confirm
  await client.query(`UPDATE tasks SET status = 'QUEUED', attempts = $2 …`);  // 2) only then mark QUEUED
}
  • Shallow queue: a 100,000-file job does not dump 20,000 tasks on the queue. If it did, a small job submitted later would wait behind them all.
  • Round-robin: with two jobs, tasks alternate between them. That is why a small job submitted after a big one finishes quickly.
  • Publish first, mark second: if the program crashes in between, the task is still PENDING and gets published again later. A duplicate is harmless. The opposite order could leave a task marked QUEUED that is not on the queue at all, and it would be stuck forever.
  • SKIP LOCKED plus an in-process lock stop the API and the scheduler from publishing the same task at the same moment.

9. The worker: pull one task, compute, report

One worker is a Python process. worker_manager.py keeps W of them running (restarts any that crash).

# worker/worker.py (simplified)
ch.basic_qos(prefetch_count=1)            # RabbitMQ hands me ONE task at a time
for method, _props, body in ch.consume("tasks", inactivity_timeout=1):
    task = json.loads(body)
    signal.pthread_sigmask(signal.SIG_BLOCK, {signal.SIGTERM})   # don't get interrupted mid-write

    set status BUSY in the workers table
    if the job is CANCELLED or FAILED:  report SKIPPED
    elif more than 5 inputs:            report FAILED "fan-in > 5"
    else:
        try:
            if task["type"] == "GENERATE": outputs = compute.generate_files(…)
            else:                           outputs = compute.combine(…)
            status = "DONE"
        except Exception as e:
            outputs, status, error = [], "FAILED", str(e)
        if slowdown > 1: time.sleep((slowdown - 1) * elapsed)    # demo: pretend to be slow
        report(task, status, outputs, …)                          # publish result, wait for confirm

    ch.basic_ack(method.delivery_tag)       # ONLY NOW tell RabbitMQ the task is finished
    signal.pthread_sigmask(signal.SIG_UNBLOCK, {signal.SIGTERM})
    set status IDLE

Why it is written this way

  • prefetch = 1 is the whole load-balancing algorithm. A worker asks for a new task only when it finishes the last one. A fast worker finishes more tasks and so takes more. No central "assign work to worker 3" logic is needed. (In our test the 3×-slower worker completed 248 tasks while each fast worker completed about 555, so it did roughly 45% as many.)
  • Ack after reporting. If the worker dies mid-task, the task was never acked, so RabbitMQ hands it to another worker. Nothing is lost.
  • The worker is stateless. It never writes tasks or items. It only runs a task and reports. All decisions live in the scheduler, so there are no races between workers.
  • 5-file limit, in layers: the scheduler never creates a task with more than 5 inputs; the worker refuses one; combine() loads one file at a time into a running total; and each worker process has a 512 MB memory cap (RLIMIT_AS) so a bug cannot silently use more.
  • Heartbeat thread: every 2 s the worker updates last_seen in the database. The scheduler marks a worker DEAD after 10 s of silence.

10. The scheduler: handling one result

The scheduler listens to the results queue and handles one result at a time, each in a single database transaction.

// api/src/scheduler.ts
channel.consume(RESULTS_QUEUE, (raw) => {
  chain = chain.then(async () => {
    await applyWorkerResult(JSON.parse(raw.content.toString()));   // all DB changes, one transaction
    channel.ack(raw);                                         // ack ONLY after the commit
    await publishPendingTasks();                                           // top up the task queue
  });
});
// api/src/results.ts: applyWorkerResult (the important branches)
lock the task row; if it is already DONE        → "duplicate ignored", stop
lock the job row; if job cancelled/failed       → mark task FAILED "job not active", stop

if result is FAILED:
    attempts >= 3 ? mark task + job FAILED : set task back to PENDING (it will be re-published)

mark task DONE; job PENDING → RUNNING
if GENERATE:         insert each output as a READY item; files_generated += n
else if final task:  count == F ? job COMPLETED (result_path set) : job FAILED "count mismatch"
else (combine):      insert the partial as a READY item

if job still RUNNING: planCombineTasks(…)      // maybe create the next COMBINE task
write an event line (shown in the dashboard log)
  • One transaction = a crash can never leave "task marked done but item not saved". Either all of it happened or none.
  • Commit, then ack. If the scheduler dies after committing but before acking, the same result is redelivered. Step 1 notices the task is already DONE and ignores it. This "at least once delivery + idempotent handling" pattern is what makes every failure safe.
  • Unique output paths (ON CONFLICT (path) DO NOTHING) mean a duplicated result cannot add the same file to the basket twice.
  • There is exactly one scheduler, so only one component ever changes the basket. That removes the whole class of "two workers grabbed the same files" bugs.

11. The planner: when to combine

After every result, planCombineTasks() looks at the job's basket (READY items) and decides whether to create COMBINE tasks. Four rules, tried in order:

// api/src/planner.ts (the loop)
for (;;) {
  if (ready.length >= 5) {                         // Rule 1: a full group of 5
    take = first 5
    isFinal = (nothing left in basket) && inFlight == 0 && allFilesGenerated
    createCombine(take, isFinal); continue;
  }
  if (ready.length >= 2 && inFlight == 0 && allGenerated) {   // Rule 2: nothing else can arrive
    createCombine(all ready, final = true); break;
  }
  if (ready.length >= 2 && fleetIdle) {                       // Rule 3: a worker is idle, don't let it sit
    createCombine(all ready, final = false); break;
  }
  if (ready.length == 1 && inFlight == 0 && allGenerated) {   // Rule 4: only a divide is left
    createCombine([the one item], final = true); break;
  }
  break;                                              // otherwise: wait for more items
}
RulePlain EnglishWhy
15 items ready → combine 55 is the biggest allowed, so it needs the fewest tasks
22+ ready, nothing running, all files exist → FINAL task with everythingThis is how the system knows the job is finished
32+ ready and a worker is idle with an empty queue → combine what is thereNo idle time while waiting for a "full" group of 5
4Exactly 1 item left and nothing else coming → a final task with one inputThe mean still needs the divide step

The final task is only created when everything left fits in it (≤ 5), nothing is in flight, and every file has been generated. Then count == F is checked as a safety net. I tested this planner with 920 randomized simulations (random speeds and completion orders) plus 7 scenarios against the real database.

The scheduler also re-runs the planner every 500 ms (the "tick"), so Rule 3 fires as soon as a worker becomes idle, even if no result happened to arrive at that moment.

12. When things go wrong

SituationWhat happensCode
A worker crashes mid-taskThe task was never acked, so RabbitMQ redelivers it to another worker. The manager restarts the crashed one. The final result is still correct (tested with kill -9).worker.py ack order
A worker hangs (no heartbeat for 10 s)Marked DEAD and an event is logged. It returns to IDLE when heartbeats resume.services/worker-health.ts / straggler-backups.ts markDeadWorkers
A task fails (an error)The worker reports FAILED. The scheduler retries up to 3 times, then fails the job with the error message.services/result-handler.ts
The same result arrives twiceThe second is ignored because the task is already DONE.services/result-handler.ts
The scheduler restartsUnacked results are redelivered, and all state is in PostgreSQL, so nothing is lost.commit-then-ack
A user cancels a jobJob → CANCELLED. Its PENDING tasks → FAILED "cancelled". Tasks already on the queue come back as SKIPPED, late results are ignored, and the queue slots go to other jobs.http/jobs-routes.ts DELETE
One worker is very slowWhen a worker is idle and the queue is empty, the scheduler publishes a backup copy of a task that has run over 2× the median time. The first result wins and the second is ignored.services/worker-health.ts / straggler-backups.ts publishStragglerBackups
You scale W down mid-jobThe manager sends SIGTERM. The worker finishes its current task, then exits ("draining"). No task is interrupted.worker_manager.py, worker.py
The three layers that make duplicates and crashes safe: (1) results for already-DONE tasks are ignored, (2) every output path is unique per task and enforced by the database, (3) the final count must equal F. A task may run twice, but it can never be counted twice.
