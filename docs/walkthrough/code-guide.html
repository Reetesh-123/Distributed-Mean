Code guide, in the order a job flows

Every file in the project, with what it does and why it is written that way. Read top to bottom: the stages follow one job from the request to the finished file.

Overview

Three rules to keep in mind while reading.
1. Every result is sums + a count, never an average. Only the last task divides.
2. Messages and the database hold paths and counts. The numbers only live in files on the shared disk.
3. Nothing is trusted to succeed. Every step can be repeated safely, so crashes only cause a retry.

File map

Paths are under services/api/src/ (TypeScript) and services/worker/distributed_mean/ (Python) unless shown in full.

1Foundations

Things every other file leans on. You do not need to memorize them. Skim now, come back when a later file mentions them.

docker-compose.yml→db/schema.sql→config→domain/statuses.ts→domain/messages.ts→infrastructure/database.ts→infrastructure/message-broker.ts
docker-compose.ymlYAML
What

Describes the five programs that make up the system: PostgreSQL, RabbitMQ, the API, the scheduler and the workers. Also their settings and the shared ./data folder.

Why

One command (docker compose up) starts everything the same way on any machine. The API and scheduler use the same code image and differ only by the start command, so there is one codebase to build.

Talks to: every service below.

Key code
services/api/Dockerfile · services/worker/DockerfileDocker
What

Build recipes. The API image installs packages, compiles TypeScript to JavaScript and copies the dashboard. The worker image installs Python packages.

Why

The worker image sets OPENBLAS_NUM_THREADS=1 and MALLOC_ARENA_MAX=1. The 512 MB memory cap counts virtual memory, and extra threads and allocator pools would hit it even though little real memory is used.

db/schema.sqlSQL
What

The database tables: jobs (one per request), tasks (units of work), items (data files: raw files and partial results), workers (heartbeats), settings (desired worker count) and events (activity log).

Why

The database is the single source of truth, so a restarted process can pick up where it stopped. CHECK constraints reject impossible statuses. items.path is UNIQUE, so a duplicate result cannot insert the same item twice. An index on pending tasks keeps scheduling fast.

Used by: nearly every file in services/ and repositories/.

Key code
config/index.tsTS· worker: config.pyPY
What

Reads every setting from environment variables once and exports it as a typed object: database and queue URLs, the 5-input limit, tick interval, retry limit, heartbeat timeout, straggler factor.

Why

Settings live in one place with sensible defaults, so no file reads process.env on its own. Required values (database, queue) fail immediately at start-up with a clear message instead of failing later at random.

Used by: task-dispatcher, combine-planner, result-handler, scheduler, workers.

Key code
domain/statuses.tsTS
What

Named constants for every status string: job (PENDING, RUNNING, COMPLETED, FAILED, CANCELLED), task type and status, item state (READY, USED), worker status, result status.

Why

Typing "COMPLETD" by mistake would silently never match. With constants the compiler catches it. The values equal the ones in schema.sql and in the Python worker.

Key code
domain/messages.tsTS· domain/rows.ts
What

TaskMessage (scheduler to worker) and TaskResultMessage (worker to scheduler), plus the shape of database rows in rows.ts.

Why

This is the contract between the TypeScript side and the Python side. A task carries fileIndexes or inputs: [{path, count}], and a result carries outputs: [{path, count}]. Never the numbers: messages stay tiny even when C is a million.

Key code
infrastructure/database.tsTS· sql-fragments.ts
What

A connection pool plus withTransaction(work): begin, run the work, commit, or roll back if it throws. sql-fragments.ts holds the one shared SQL condition "this worker's heartbeat is recent".

Why

Many steps must succeed or fail together (for example: mark task done, add items, plan the next task). One helper guarantees nothing is left half-done. A shared fragment avoids copying the heartbeat condition into four places.

Used by: result-handler, task-dispatcher, job-service, scheduler.

Key code
infrastructure/message-broker.tsTS
What

Connects to RabbitMQ, declares the two queues (tasks, results) and offers publish(queue, message).

Why
  • Retry on connect: RabbitMQ answers its health check slightly before it accepts connections.
  • Durable queue + persistent messages: they survive a broker restart.
  • Confirm channel: publish resolves only after the broker has stored the message, so "published" really means published.

Used by: task-dispatcher, backup-copies, scheduler.

2Submit a job

A user calls POST /jobs {"F":12,"C":3}. The API checks the request, stores the job, cuts it into small GENERATE tasks, and answers right away. It does not wait for the work.

entrypoints/api-server.ts→http/jobs-routes.ts→http/validation.ts→services/job-service.ts→repositories/event-repository.ts
entrypoints/api-server.tsTS
What

Starts the Express web server, registers the routes, serves the dashboard and has one last error handler.

Why

It is only wiring: no logic. The error handler logs the real error but returns a generic 500, so internal details never leak to users.

Calls: jobs-routes, stats-routes, workers-routes.

http/validation.tsTS· http/async-handler.ts
What

validateJobSize checks 1 < F < 100000 and 1 < C < 1000000. isUuid checks ids. asyncHandler forwards errors from async routes to the error handler.

Why

Reject bad input with a clear 400 before anything is stored. Express 4 does not catch rejected promises, so without asyncHandler a database error would hang the request.

http/jobs-routes.tsTS
What

The job endpoints: POST /jobs, GET /jobs, GET /jobs/:id, GET /jobs/:id/result, DELETE /jobs/:id. Each handler validates, calls one function, and sends the reply.

Why

Routes are thin on purpose: HTTP in, one service call, HTTP out. POST returns 202 Accepted because the job is only accepted, not finished.

Calls: validation, job-service, job-repository.

Key code
services/job-service.tsTS
What

createJob: inserts the job and, in the same transaction, one GENERATE task per group of 5 files (F = 12 gives tasks for files 0–4, 5–9, 10–11), then calls the dispatcher. cancelJob: marks a job CANCELLED and drops its unpublished tasks.

Why

Job and tasks are saved in one transaction, so a job never exists without its tasks. Chunks of 5 respect the per-worker limit from the very first step. Splitting is done in SQL (generate_series) so even F = 99,999 is one fast statement.

Called by: jobs-routes. Calls: publishPendingTasks, recordEvent.

Key code
repositories/event-repository.tsTS
What

recordEvent(jobId, message) adds a line to the events table.

Why

This feeds the dashboard's live activity log. It accepts the current transaction as a parameter, so a log line is saved or rolled back together with the change it describes.

3Publish tasks to the queue

Tasks now sit in the database as PENDING. The dispatcher moves some of them into the RabbitMQ queue. It does not push everything, only a few at a time.

services/fleet-state.ts→services/task-dispatcher.ts→infrastructure/message-broker.ts
services/fleet-state.tsTS
What

getFleetSnapshot() returns four numbers: desired workers, idle workers, busy workers, and tasks waiting in the queue (queued minus busy).

Why

Both the dispatcher ("how many more tasks should I publish?") and the planner ("is a worker idle?") need the same picture of the fleet. Only workers with a recent heartbeat count, so dead ones never look available.

Used by: task-dispatcher, result-handler, scheduler.

services/task-dispatcher.tsTS
What

publishPendingTasks() publishes PENDING tasks until the queue holds about 2 × workers tasks, one task per job in turn (round-robin). buildTaskMessage turns a task row into the message a worker receives.

Why
  • Shallow queue: a huge job cannot fill the queue and starve a small job that arrives later.
  • Round-robin: the 1st task of every job, then the 2nd of every job.
  • Publish first, then mark QUEUED: a crash in between only republishes, which is harmless.
  • One run at a time: overlapping calls would double-fill the same slots.

Called by: job-service, scheduler (after every result and every tick).

Key code

4A worker runs a task

The worker side is Python. A manager keeps the right number of worker processes alive. Each worker takes one task, runs it, saves files, and reports back. First task type: GENERATE.

worker_manager.py→worker.py→computation.py→file_storage.py
worker_manager.pyPY
What

Every 2 seconds it reads desired_workers from the database, starts missing worker processes and tells surplus ones to stop (SIGTERM).

Why
  • Separate processes run truly in parallel, and one crashing does not take the others down. The manager restarts it.
  • The count is a database setting, so PUT /workers or the dashboard can scale up or down without restarting anything.
  • Scale-down uses SIGTERM, so a worker finishes its current task first (a graceful drain).

Starts: worker.py.

Key code
worker.pyPY
What

One worker process. It connects, registers itself in the workers table, starts a heartbeat thread, then loops: take a task, run it, publish the result, acknowledge it.

Why
  • prefetch = 1: the broker gives a worker the next task only when it finishes the last, so faster workers do more automatically.
  • Ack after publishing the result: if the worker dies earlier, the broker redelivers the task to someone else.
  • Heartbeat thread: "no heartbeat for 10 s" is how the scheduler spots a dead worker.
  • SIGTERM blocked during a task: a signal in the middle of a file write could leave a broken file.
  • Errors become FAILED results, not crashes. The scheduler decides about a retry.
  • Re-checks the 5-input limit even though the scheduler already enforces it (defence in depth).

Calls: computation. Reports to: scheduler through the results queue.

Key code
computation.pyPY· first half: generate_files
What

generate_files creates up to 5 files of C random numbers, saves each as raw/00000.npy and returns one item {path, count: 1} per file.

Why

A raw file is already a valid item (sums = itself, count = 1), so the same combine code handles files and partial results. The seed is derived from job id and file index, so a retried or duplicated task writes identical data, and verify.py can recompute the truth later.

Writes via: storage.

Key code
file_storage.pyPY
What

Three helpers: save a NumPy array, save a CSV, load an array.

Why
  • Atomic write: write to a temporary file, then rename. A crash or a duplicate task never leaves a half-written file at the real path.
  • Memory-mapped load: reading does not copy the whole array into RAM.
  • Length check: a file of the wrong length would silently shift positions, so it raises an error instead.

5The scheduler receives the result

The worker's message arrives on the results queue. The scheduler is the only part that changes job state. It handles results one at a time, each in a single database transaction.

entrypoints/scheduler.ts→services/result-handler.ts→services/combine-planner.ts
entrypoints/scheduler.tsTS
What

Process 2. It does two jobs: (a) consume result messages one at a time; (b) every 500 ms run a tick (dead-worker check, re-plan, backups, publish pending tasks).

Why
  • Ack only after the transaction commits. If it crashes in between, the message is redelivered. Because handling is idempotent, nothing breaks.
  • Failed handling is nacked back to the queue after a 1 s pause, avoiding a tight loop.
  • Strict order, one at a time: no two results for the same job race each other.
  • The tick exists because some decisions depend on time or on a worker becoming idle, not on a new result.
  • Single instance keeps the planning logic simple.

Calls: applyWorkerResult, publishPendingTasks, planCombineTasks, markDeadWorkers, publishBackupCopies.

Key code
services/result-handler.tsTS
What

applyWorkerResult turns a worker's report into database changes: lock the task and job; ignore it if the task is already DONE or the job is cancelled; on failure retry or fail the job; on success mark the task DONE, add the new items to the waiting items (READY), complete the job if it was the final task, then ask the planner for new work.

Why
  • One transaction: everything above succeeds or nothing does.
  • Idempotent: a duplicate result (backup copy, redelivery) is ignored, and ON CONFLICT DO NOTHING on items.path blocks double inserts.
  • Row locks (FOR UPDATE) make concurrent updates to the same job wait.
  • Count check: the final task's count must equal F, otherwise the job is FAILED rather than returning a wrong mean.
  • Retry limit (3): a task that keeps failing fails the job instead of looping forever.

Called by: scheduler. Calls: planCombineTasks, getFleetSnapshot.

6Planner and combine: the heart

New items join the waiting items. The planner decides whether to create a COMBINE task now. A worker then runs it with combine_items, and the new partial goes back to the waiting items. This repeats until one item covers all F files.

services/combine-planner.ts→task-dispatcher→worker.py→computation.py (combine)→result-handler
services/combine-planner.tsTS
What

planCombineTasks looks at one job's READY items and creates COMBINE tasks by four rules:
1 5 or more items are waiting: combine 5 now.
2 all files generated and nothing else running: combine everything left as the final task.
3 a worker is idle and the queue is empty: combine what is there (at least 2).
4 one item left and all done: a final task that only divides.
Otherwise: wait.

Why
  • No waiting for rounds: combining starts while other files are still being generated, so workers stay busy.
  • Items become USED immediately when the task is created, so no other task can take them.
  • Partials and raw files mix freely because every item carries its own count.
  • Rule 3 avoids an idle worker. Rule 2 is the only place a task becomes final, and it requires nothing else to be in flight.
  • Never more than 5 inputs per task.

Called by: result-handler (after each result), scheduler tick.

Key code
computation.pyPY· second half: combine_items
What

Adds up to 5 items position by position and adds their counts. Not final: saves the running sums as a new partial. Final: divides by the total count once and writes result.npy and result.csv.

Why
  • Sums and counts, not averages: groups have uneven sizes, and only sums can be merged in any order.
  • One input in memory at a time plus the running total: this is how the 5-file RAM limit is respected.
  • float64 total keeps precision when many values are added.
  • Divide only in the final task, and report the total count so the scheduler can check it equals F.

7Finish and observe

When the final task's count equals F the job is COMPLETED. The rest of the code lets people see what is happening and fetch the answer.

jobs-routes (GET)→job-repository.ts→stats / workers routes→public/index.html→verify.py
http/jobs-routes.tsTS· GET /jobs/:id and /result
What

GET /jobs/:id returns status, progress and task counts. GET /jobs/:id/result downloads the CSV if COMPLETED, otherwise 409.

Why

The client polls instead of waiting on an open connection, so jobs can take minutes. 409 tells a client "not ready yet" without being an error.

repositories/job-repository.tsTS
What

Read queries for jobs: list, one job with task counts, and the result path. Also the progress formula.

Why

Keeping SQL in repositories keeps routes readable. Progress = (files generated + merges done) / (2F − 1): F generations plus F−1 merges. It is capped at 99 until COMPLETED, so it never shows 100 while work remains.

http/stats-routes.ts · http/workers-routes.tsTS· repositories/stats-repository.ts · worker-repository.ts
What

GET /stats: counts of workers, jobs and tasks plus retries and backups. GET /events: the activity log. GET /workers: the worker table. PUT /workers {count}: set the worker count (0 to 32).

Why

These power the dashboard and make the system observable. A worker whose heartbeat is stale is reported as DEAD even if its stored status says BUSY. /events?after=ID lets the UI fetch only new lines.

Reads the tables from schema.sql. PUT /workers only writes a setting; worker_manager.py reacts to it.

services/api/public/index.htmlHTML/JS
What

A single-page dashboard with no build step. Every second it calls /stats, /workers, /jobs and /events and redraws counters, tables and the log. It has a form to create jobs, a worker-count control and cancel/download buttons.

Why

Plain polling is simple and robust. The UI contains no business logic: it only calls the same public API as any other client.

verify.pyPY
What

Recomputes the mean directly from the raw files (adding them one by one) and compares it with result.npy. Passes if the largest difference is at most 1e-9.

Why

An independent check that the distributed pipeline produced the right answer. It does not use partials, so a bug in the combining logic cannot hide.

8When things go wrong

None of these needs special operator action. They are handled by the same flow, with a few small extra items.

worker-health.ts·backup-copies.ts·retries·cancel
services/worker-health.tsTS
What

markDeadWorkers sets workers with no heartbeat for 10 s to DEAD and logs it once.

Why

The dashboard and the planner must not count a frozen worker as available. The task it held is not lost: it was never acknowledged, so RabbitMQ redelivers it. If the worker wakes up, its heartbeat sets it back to IDLE.

services/backup-copies.tsTS
What

If a worker is idle and nothing waits in the queue, publish a duplicate of a task that has run longer than 2 × the median (and at least 1 s).

Why

A slow worker should not delay the end of a job. The first copy to finish wins; the later result is ignored as a duplicate. It only fires when a worker would otherwise be idle, so it never steals capacity from real work.

Key code
result-handler.ts · handleFailedTaskTS
What

If a worker reports FAILED: below 3 attempts the task goes back to PENDING and is published again; at 3 attempts the job is marked FAILED with the error.

Why

Temporary problems (a busy disk) should not fail a whole job, but a task that never works must not loop forever. Retries are safe because tasks write to fixed or unique paths.

job-service.ts · cancelJobTS
What

DELETE /jobs/:id marks the job CANCELLED and its unpublished tasks FAILED. Tasks already in the queue are skipped by workers (SKIPPED), and late results are discarded.

Why

Cancelling must be fast and must not corrupt anything. Workers never need to be interrupted, and the freed queue slots go straight to other jobs.

9Scripts and tests

scripts/·tests·bench/
scripts/demo.sh · scripts/kill-worker.shBash
What

demo.sh creates a job, waits for it, downloads the CSV and runs verify.py. kill-worker.sh sends kill -9 to one worker process.

Why

One command that proves the whole system works end to end, and a crash test that shows a killed worker does not break the result: the task is redelivered and the manager restarts the worker.

services/worker/tests/test_computation.py · services/api/tests/integration/*.jsTests
What

Python unit tests for the maths (the assignment example, uneven groups, mixed partial and raw inputs, size limits). Integration tests run the planner rules and applyWorkerResult against a real database inside rolled-back transactions.

Why

The two risky parts are the arithmetic and the scheduling decisions. The unit tests need no services at all. The integration tests check the planner and result handler on real SQL, including duplicates, retries and a wrong final count.

bench/simulate.py · bench/planner_check.pyPY
What

simulate.py compares four scheduling strategies on workers of different speeds. planner_check.py runs the waiting items rules on random jobs and asserts a correct mean, count = F, no task over 5 inputs and no deadlock.

Why

These are quick, standalone models used to choose the design and to test the planner rules before touching the real system.
